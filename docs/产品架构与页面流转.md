# 产品架构与页面流转

这份文档说明 `materials-demo-teaching` 的产品结构、页面流转和前后端职责。

目标读者：

- 需要继续改前端体验的人
- 需要把当前工作台接到更完整后端的人
- 需要快速理解当前工作台与 `material-agent` 关系的人

## 1. 设计目标

核心目标有三个：

1. 前端交互参考 `material-agent/frontend`
2. 把前端收口到本仓库自己的 `frontend-next/`
3. 入口改成 prompt-only，由后端统一做意图解析和参数补全

因此当前方案是：

- 交互层参考 `material-agent`
- 前端层使用 `Next.js`
- 工作流层继续使用本项目的任务存储与 MCP 链路

## 2. 页面结构

当前前端分为两种主视图：

### 2.1 Compose View

用于发起新任务。

包含：

- prompt 输入框
- 示例任务 chips

特点：

- 不再要求显式输入 `formula / num_samples / relax`
- 只负责发起任务，不承载复杂结果展示

### 2.2 Summary View

用于查看已有任务结果。

包含：

- 顶部任务摘要
- 工作流进度
- 消息流
- 总览 / 参考材料 / 候选结果 / trace
- 路由决策面板
- 产物下载面板

特点：

- 已有历史任务时，页面默认进入这里
- 这是当前工作台的主要展示形态

## 3. 左侧历史任务栏

左侧任务栏参考 `material-agent` 的时间分组方式。

当前实现：

- 今天
- 昨天
- 最近 7 天
- 更早

每条历史任务卡片展示：

- 标题
- prompt 摘要
- 解析出的 formula
- 运行状态
- 候选数量
- 更新时间

点击任意任务：

- 会加载 `/api/tasks/{id}`
- 直接切到 Summary View

这就是“已有历史任务时默认进入结果页”的具体实现方式。

## 4. 默认进入结果页的规则

页面初始化时：

1. 先请求 `/api/tasks`
2. 如果有任务，默认选中最新一条
3. 自动切到 Summary View
4. 再请求 `/api/tasks/{id}` 拉详情

只有在以下情况才停留在 Compose View：

- 当前没有历史任务
- 用户主动点击“发起新任务”

## 5. prompt-only 输入链路

前端提交 payload：

```json
{
  "prompt": "...",
  "reuse_existing": true
}
```

后端在进入工作流前做 `normalize_run_request`，补齐：

- `formula`
- `num_samples`
- `relax`

规则来源：

- [app/workflow.py](../app/workflow.py)

当前解析策略是两层结构：

1. 如果配置了 `LLM_ROUTER_BASE_URL / LLM_ROUTER_API_KEY / LLM_ROUTER_MODEL`，优先让 LLM 返回结构化参数：
   - `formula`
   - `num_samples`
   - `relax`
2. 如果 LLM 未配置、调用失败或返回结果不完整，则回退到本地规则兜底

当前规则兜底包括：

- 化学式用正则抽取
- 样本数从 “生成 3 个 / generate 3 candidates” 一类表达提取
- 弛豫根据 “弛豫 / relax / 不做弛豫 / without relax” 判断

## 6. 前后端职责边界

### 前端职责

前端只负责：

- 输入 prompt
- 创建任务
- 切换视图
- 轮询历史与详情
- 展示状态、消息、trace 和产物

前端不负责：

- 解析材料意图
- 决定是否检索 / 生成 / 评估
- 复现后端工作流逻辑

### 后端职责

后端负责：

- 规范化输入
- 管理任务持久化
- 执行工作流
- 路由到 MCP 工具
- 增量回写任务状态

## 7. 后端主要模块

### 7.1 `app/main.py`

职责：

- 暴露 API
- 提供后端入口与跳转
- 创建后台任务
- 提供任务查询和文件下载接口

### 7.2 `app/workflow.py`

职责：

- 解析输入
- 路由决策
- 调用 MCP
- 汇总参考材料、候选结构、评估结果和 trace

### 7.3 `app/task_store.py`

职责：

- 任务持久化
- 任务去重复用
- 增量状态更新

### 7.4 `app/models.py`

职责：

- 定义请求与任务模型

## 8. 工作流节点职责

### `parse_input`

把自然语言 prompt 规范化成结构化运行参数。

### `decide_next_step`

决定是否执行：

- 参考检索
- 候选生成
- 结构评估

### `lookup_reference_materials`

调用 `materials-project` MCP。

### `generate_structures`

调用 `material-agent-core` 的 MatterGen 生成能力。

### `evaluate_structures`

调用 `material-agent-core` 的 MatterSim 评估能力。

### `finalize`

整理任务结果供 API 和前端显示。

## 9. 前端部署方式

当前前端已经迁到 `frontend-next/`，运行方式是：

1. `FastAPI` 继续提供 `/api/tasks`、`/api/file` 等后端接口
2. `Next.js` 前端独立运行在 `3000`
3. 访问 `18018/` 时，后端会跳转到 `3000`

## 10. 后续扩展建议

如果要继续扩展，可以优先按下面顺序推进：

1. 增加单独的任务详情路由页
2. 增加结构化报告导出
3. 增加更强的 prompt 解析层
4. 对齐 `material-agent` 的更多结果组件，如工作流画布、报告预览等

## 11. 核心结论

如果只记三件事，优先记这三条：

1. 前端已经是 prompt-only，不再依赖显式公式/样本数/弛豫输入
2. 有历史任务时，页面默认直接进入结果页
3. 前端交互参考了 `material-agent`，但实现已经收口到本仓库自己的 `frontend-next/`
